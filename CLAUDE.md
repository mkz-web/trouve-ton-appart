## Positionnement (résumé public des décisions du 10/06/2026)

- **Périmètre géographique** : Paris et Île-de-France uniquement.
- **Trois publics, trois parcours** : étudiants et jeunes actifs ; publics fragiles (logement social, seniors, PMR, urgence) ; mobilité professionnelle et expats (meublé, bail mobilité, relocation).
- **Un guichet d'orientation, pas un portail d'annonces de plus** : le site capte la demande informationnelle, explique les dispositifs et renvoie vers les guichets officiels. Le dépôt d'annonces n'est envisagé qu'en phase 3, si traction.
- **Collecte de données** : open data (CROUS, RPLS, FINESS, DRIHL, opendata.paris.fr, API Géo) et liens sortants. **Jamais de scraping des portails d'annonces** (jurisprudence Leboncoin c. Entreparticuliers, CA Paris 2021).
- Le détail de l'étude fondatrice (demande mesurée, concurrence, segment d'attaque, monétisation) est dans le journal privé.

## Architecture technique (3 phases)

1. **Phase 1** : site statique généré par script **Node pur autonome** (règle MKZ) : pages profil × dispositif × commune depuis JSON. Hébergement statique. Indexation via MCP GSC.
2. **Phase 2** : ingestion open data (scripts Node natifs `https`) → JSON local → régénération. Recherche client-side sur index JSON.
3. **Phase 3** (si traction) : flux partenaires, Postgres + Meilisearch, alertes. Décision d'investissement séparée.

- **Contrôle de rendu ajouté (19/07/2026)** : `node site/check-rendu.js`, **zéro dépendance** (Node 22+ pour la WebSocket native, pilote un Chrome ou Edge **déjà installé** via le protocole DevTools, sert `dist/` par un serveur éphémère). Motif : `check-links` et `check-seo` lisent le HTML, ils ne voient donc **jamais** un défaut de mise en page. Deux bugs bien visibles à l'œil sont passés au travers (champs de formulaire en escalier parce que les libellés faisaient 1, 2 et 3 lignes ; légende de `fieldset` à cheval sur son cadre, qui est le rendu natif du navigateur). Le script mesure la page **rendue** sur 18 gabarits × 3 largeurs (375, 768, 1280) et détecte : scroll horizontal, élément hors de son conteneur, chevauchement de blocs, texte tronqué, champs d'une rangée désalignés, cible sous 24 px (WCAG 2.5.8), région `aria-live` sans `aria-atomic` ou masquée, légende à cheval. Options : `--toutes` (les 66 pages), `--page /outils/`, `--largeurs`, `--verbeux`. ⚠️ **Il ne juge pas l'esthétique** : un champ mal aligné sous son libellé reste géométriquement « correct ». L'œil humain reste le meilleur détecteur pour cette catégorie, le script attrape les régressions. Faux positif câblé : une marge négative compensant un padding (zone cliquable élargie sans décalage du texte, utilisée par le sommaire des guides) n'est pas un débordement. ⚠️ **Leçon de sa mise au point, valable pour tout contrôle automatisé** : la première version annonçait « OK : aucun défaut » alors qu'elle auditait `/background.html`, une cible interne de Chrome (`/json/new` exige **PUT** sur les Chrome récents, et le repli prenait la première cible de `/json/list`). Un contrôle qui échoue en silence est **pire que pas de contrôle**, puisqu'il certifie le contraire de la vérité. D'où la méthode de validation retenue, à rejouer à chaque évolution du script : **réintroduire volontairement les défauts déjà corrigés et vérifier qu'ils sont détectés**, avant de vérifier qu'un build sain passe. Quatre garde-fous en découlent dans le code (exception JS remontée, résultat d'audit vide refusé, URL réellement auditée comparée à l'URL demandée, largeur appliquée vérifiée) et le message « OK » n'est jamais affiché si un rendu n'a pas pu être audité.
